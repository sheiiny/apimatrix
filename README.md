# ToolCabinetApi

Учебный сервер для дипломного проекта: связь ERP с инструментальным шкафом MATRIX-TM. Реализованы минимальный API, запуск через Docker и конфигурация CI/CD для Windows-стенда. База данных и функции выдачи инструмента будут добавлены позже.

По решению пользователя используется **.NET 10**, хотя в исходном задании был указан .NET 8. Версия SDK задана в `global.json`: подходит стабильный SDK 10.0.100 или более новый из ветки 10.0.

## Запуск и проверка

Из корня репозитория, после установки .NET SDK 10:

```powershell
dotnet restore ToolCabinetApi.slnx
dotnet build ToolCabinetApi.slnx --configuration Release --no-restore
dotnet test ToolCabinetApi.slnx --configuration Release --no-build
dotnet run --project src/ToolCabinetApi --configuration Release --no-build --no-launch-profile --urls http://127.0.0.1:5080
```

В другом терминале:

```powershell
curl.exe -i http://127.0.0.1:5080/api/v1/health
```

Ожидается HTTP `200 OK` и JSON `{"status":"ok"}`. Маршрут проверяет только работу процесса API и приём запросов; SQL Server он не проверяет. Остановить сервер можно сочетанием Ctrl+C.

Интеграционный тест запускает настоящее приложение через `WebApplicationFactory`, отправляет HTTP-запрос и проверяет статус 200, тип содержимого и JSON с единственным полем `status`, равным `ok`.

На этом компьютере SDK 10 установлен локально в `.tools/dotnet`, системный SDK не менялся. Чтобы пользоваться им в текущем PowerShell:

```powershell
$env:PATH = "$PWD\.tools\dotnet;$env:PATH"
$env:DOTNET_ROOT = "$PWD\.tools\dotnet"
$env:DOTNET_CLI_HOME = "$PWD\.tools\cli"
$env:NUGET_PACKAGES = "$PWD\.tools\packages"
dotnet --version
```

Папка `.tools` исключена из Git. После клонирования на другом компьютере достаточно установить SDK 10 обычным способом.

## Запуск через Docker

Нужен запущенный Docker Desktop с WSL 2 и Linux-контейнерами. Установка SDK на Windows для этого способа не требуется: приложение собирается внутри Docker.

Из корня репозитория:

```powershell
cd C:\Users\Home\apimatrix
docker compose config --quiet
docker compose up --build -d
docker compose ps
curl.exe -i http://127.0.0.1:5080/api/v1/health
```

Ожидается HTTP `200 OK` и `{"status":"ok"}`. После запуска подождите несколько секунд перед проверкой. Если API ещё не готов, посмотрите логи и повторите запрос.

```powershell
# Логи; Ctrl+C прекращает просмотр, API продолжает работать
docker compose logs -f api

# Остановить и удалить контейнер проекта
docker compose down
```

После изменения кода снова выполните `docker compose up --build -d`. Docker пересоберёт образ и заменит контейнер. Эта команда сама по себе не запускает интеграционные тесты: их нужно запускать отдельно через `dotnet test` или CI.

Внешний порт можно изменить для текущего терминала, например если 5080 уже занят локальным запуском API:

```powershell
$env:TOOLCABINET_PORT = '5081'
docker compose up --build -d
curl.exe -i http://127.0.0.1:5081/api/v1/health
```

Для возврата к порту 5080 удалите переменную и пересоздайте контейнер:

```powershell
Remove-Item Env:TOOLCABINET_PORT -ErrorAction SilentlyContinue
docker compose up -d
```

`Dockerfile` собирает Release-версию в образе SDK 10 и переносит только опубликованное приложение в образ ASP.NET Core Runtime 10. Процесс работает от непривилегированного пользователя. `.dockerignore` передаёт в сборку только `global.json` и исходники API, исключая локальные `bin` и `obj`.

`compose.yaml` запускает сервис `api` из образа `toolcabinetapi:local`. Внутри используется порт 8080, снаружи по умолчанию 5080, доступный только с этого компьютера через 127.0.0.1. Контейнер перезапускается по политике `unless-stopped`, пока Docker работает. SQL Server на этом этапе не подключается. Проверка health выполняется внешним HTTP-запросом; состояние `Up` в Compose само по себе не подтверждает ответ API.

## CI в GitHub Actions

Конфигурация: `.github/workflows/ci.yml`. Облачный runner `ubuntu-latest` запускается при push в любую ветку, кроме `main`, при pull request и вручную через **Run workflow**. Ветка `server` содержит приложение. В `main` достаточно хранить workflow для регистрации ручного запуска в GitHub; переносить туда исходники приложения не требуется.

1. Устанавливает .NET SDK 10 и восстанавливает зависимости.
2. Собирает решение в Release и запускает интеграционный тест.
3. После успеха публикует API и загружает артефакт `ToolCabinetApi-<полный SHA коммита>`.
4. Отдельная задача `Build and check Docker image` после успешного завершения первой задачи собирает Linux-образ `toolcabinetapi:<полный SHA коммита>` для `linux/amd64`.
5. Запускает временный контейнер на свободном локальном порту и проверяет HTTP 200, тип содержимого и JSON `{"status":"ok"}`. При неуспехе показывает логи и завершает задачу с ошибкой. Временный контейнер удаляется в любом случае.
6. После успешной HTTP-проверки сохраняет образ через `docker image save` и загружает артефакт `ToolCabinetApi-docker-<полный SHA коммита>`.

Внутри пакета есть `build-info.json` с SHA, репозиторием и номером запуска. В PR это SHA проверяемого merge-коммита GitHub. Результаты тестов сохраняются отдельно в TRX, в том числе при падении теста. При ошибке сборки или теста публикация приложения и загрузка его пакета пропускаются.

Docker-задача зависит от задачи сборки и тестов через `needs`, поэтому при её ошибке не запускается. Если сборка контейнера или его health-проверка завершается ошибкой, архив Docker-образа не публикуется. Обычный пакет API и Docker-образ — отдельные артефакты; для следующего этапа CD будем использовать проверенный Docker-образ.

Docker-артефакт хранится 14 дней и содержит:

- `toolcabinetapi.tar` — готовый образ, которому не нужна пересборка на стенде;
- `build-info.json` — SHA коммита, репозиторий, номер запуска, тег и ID образа, платформа и SHA256 архива.

Тег и метка образа `org.opencontainers.image.revision` содержат SHA проверяемого коммита. Внешний реестр образов и токен для него не нужны. Для первой сборки CI требуется доступ к реестру Microsoft.

Ту же HTTP-проверку можно выполнить локально для уже собранного образа:

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File scripts/Test-Container.ps1 -Image toolcabinetapi:local
```

Команда разрешает запуск сценария только для этого процесса PowerShell. Сценарий создаёт отдельный временный контейнер, не занимает порт 5080 и не останавливает Compose-сервис. Он не пересобирает образ и не скачивает отсутствующий образ из реестра.

После скачивания Docker-артефакта из Actions распакуйте его содержимое в `artifacts/docker` и проверьте загрузку, например на порту 5081:

```powershell
$info = Get-Content artifacts/docker/build-info.json -Raw | ConvertFrom-Json
$hash = (Get-FileHash artifacts/docker/toolcabinetapi.tar -Algorithm SHA256).Hash
if ($hash -ine $info.sha256) { throw 'Контрольная сумма архива не совпала' }
docker image load --input artifacts/docker/toolcabinetapi.tar
if ($LASTEXITCODE -ne 0) { throw 'Не удалось загрузить образ' }
docker run --rm --pull never -p 127.0.0.1:5081:8080 $info.image
```

В другом терминале выполните `curl.exe -i http://127.0.0.1:5081/api/v1/health`. Остановка — Ctrl+C. ASP.NET Core Runtime уже находится внутри образа, отдельно устанавливать его на стенд для контейнерного запуска не нужно.

Результат после отправки изменений: [вкладка Actions](https://github.com/sheiiny/apimatrix/actions), процесс **ToolCabinetApi CI/CD**. Для полного прогона нажмите **Run workflow**, в списке **Branch / Use workflow from** выберите `server` (или другую доверенную ветку с приложением и этим workflow), затем подтвердите запуск. GitHub запускает workflow из выбранной ветки; все три задачи явно извлекают один и тот же `github.sha`, зафиксированный при старте. Изменение ветки во время сборки не подменяет проверяемый коммит.

Кнопка ручного запуска появляется, когда workflow с `workflow_dispatch` находится в default branch (`main`). Поэтому обновлённый `ci.yml` нужно хранить и в `main`, и в ветке приложения. Из `server` в `main` переносится только `.github/workflows/ci.yml`; сценарии PowerShell, Dockerfile, тесты и исходники берутся из выбранной ветки приложения. Если вручную выбрать `main` без приложения, проверка наличия решения завершится понятной ошибкой; деплой из `main` запрещён условием задачи. Слияние всего проекта в `main` не требуется. [Документация ручного запуска GitHub Actions](https://docs.github.com/en/actions/how-tos/manage-workflow-runs/manually-run-a-workflow).

Проверить публикацию локально можно так:

```powershell
dotnet publish src/ToolCabinetApi/ToolCabinetApi.csproj --configuration Release --no-build --output artifacts/publish -p:UseAppHost=false
dotnet artifacts/publish/ToolCabinetApi.dll --urls http://127.0.0.1:5080
```

Пакет требует установленный ASP.NET Core Runtime 10. Он запускается через `dotnet ToolCabinetApi.dll` и не содержит привязанный к ОС исполняемый файл. SQL Server, токены и пароли для текущего этапа не нужны.

## CD на Windows-стенд

Задача `Deploy to Windows stand` запускается только вручную (`workflow_dispatch`) для выбранной ветки приложения, кроме `main`, после успешной Docker-задачи, если переменная репозитория `TOOLCABINET_CD_ENABLED` равна строке `true`. При обычных push и PR выполняется CI, а CD пропускается. Два развёртывания на один стенд не выполняются одновременно; начатое развёртывание не отменяется новым запуском.

На стенде должны быть запущены Docker Desktop с Linux engine и Windows runner с метками `self-hosted`, `Windows`, `X64`, `toolcabinet-stand`. Облачные задачи сборки и тестов на этот runner не назначаются. Runner должен запускаться под той же учётной записью, которая имеет доступ к Docker Desktop и каталогу стенда.

Шаг CD запускает Windows PowerShell с `-ExecutionPolicy Bypass` только для своего процесса, чтобы политика `Restricted` на компьютере не блокировала временный скрипт GitHub Actions и сценарий развёртывания. Системная и пользовательская политики выполнения не меняются. Необработанная ошибка сценария завершает шаг с ошибкой.

Runner уже зарегистрирован пользователем. Для ручного запуска после перезагрузки:

```powershell
# Сначала открыть Docker Desktop и дождаться запуска движка
docker version
cd C:\actions-runner
.\run.cmd
```

Окно оставьте открытым: `Listening for Jobs` означает готовность, а не зависание. В GitHub runner должен быть `Idle`. Для первого учебного прогона служба Windows не требуется. В этом режиме доступность после перезагрузки зависит от входа пользователя, запуска Docker Desktop и `run.cmd`.

### Настройки GitHub перед первым прогоном

В [Settings → Secrets and variables → Actions](https://github.com/sheiiny/apimatrix/settings/variables/actions), вкладка **Variables**, задайте переменные репозитория:

| Переменная | Значение для учебного стенда |
| --- | --- |
| `TOOLCABINET_CD_ENABLED` | `true` — включить CD; `false` или отсутствие переменной — пропустить CD |
| `TOOLCABINET_DEPLOY_DIR` | `C:\Users\Home\ToolCabinetApi\stand` — абсолютный путь с правом записи у пользователя runner |
| `TOOLCABINET_PORT` | `5090` — внешний порт; если переменная отсутствует, используется 5090 |

Переменную включения нужно задать именно на уровне репозитория: она проверяется до назначения задачи окружению. Порт 5090 отделяет стенд от локального Compose на 5080. Каталог стенда и подкаталоги `releases` создаёт сценарий.

В **Settings → Environments** создайте `training`. В deployment branch rules разрешите выбранную ветку приложения, например `server`, если эта возможность доступна для репозитория и тарифа. Если раньше была разрешена только `main`, замените правило на `server`: иначе GitHub заблокирует ручное развёртывание из неё. Для других веток добавляйте разрешение явно. Запускайте CD только из доверенных веток. Метка runner выбирает компьютер, но сама по себе не является ограничением доступа: не назначайте этому runner задачи из недоверенных PR или других workflow.

Токен регистрации runner вводится один раз при настройке на стенде; в файлы проекта он не добавляется. Для скачивания артефакта workflow использует штатный `GITHUB_TOKEN`. Дополнительные пароли и токен реестра для этого этапа не нужны. В будущем секреты подключения к БД нужно задавать средствами GitHub или настройками стенда.

### Как проходит развёртывание

1. Windows runner скачивает `ToolCabinetApi-docker-<SHA>` из того же запуска CI.
2. `scripts/Deploy-Container.ps1` проверяет SHA коммита, репозиторий, номер запуска и SHA256 архива.
3. Сохраняет пакет в `<каталог стенда>/releases/<SHA>-<номер запуска>`, загружает через `docker image load` и сверяет ID, платформу и метку коммита образа. Пересборки и скачивания образа из реестра на стенде нет.
4. С краткой остановкой заменяет контейнер `toolcabinet-stand`. Сценарий управляет только контейнером со своими метками и своим каталогом установки.
5. Проверяет, что запущен ожидаемый образ, и отправляет запрос на `/api/v1/health`. Нужны HTTP 200, `application/json` и JSON с единственным полем `status`, равным `ok`.
6. После успеха записывает `<каталог стенда>/current.json`: коммит, запуск CI, образ, ID, контейнер, порт и время UTC. Сохранённые пакеты остаются в `releases`.

Если новая версия не проходит проверку, сценарий удаляет её контейнер и возвращает предыдущий, проверяя его на прежнем порту. CD остаётся неуспешным даже при успешном откате. При первой установке без предыдущей версии неуспешный контейнер удаляется. Логи неуспешной версии сохраняются как `failed-container.log` в папке её пакета, когда их удаётся получить. При отключении питания или принудительном завершении процесса автоматический откат не гарантируется.

Проверка стенда после успешного CD:

```powershell
curl.exe -i http://127.0.0.1:5090/api/v1/health
docker logs --tail 50 toolcabinet-stand
Get-Content C:\Users\Home\ToolCabinetApi\stand\current.json
```

Доступ по умолчанию только с компьютера стенда, через 127.0.0.1. Реальный CD проверяется ручным запуском выбранной ветки через **Run workflow**. В Actions должны успешно завершиться все три задачи, затем версия в `current.json` должна совпасть с коммитом выбранной ветки на момент запуска. При ошибке сборки или тестов задача Docker пропускается, а вместе с ней и CD.

## Состояние этапа

Готовы API с проверками, локальный запуск через Docker и конфигурация CI/CD. Пользователь зарегистрировал и запустил Windows runner, создал переменные и окружение. Текущая настройка ручного выбора ветки ещё не закоммичена и не отправлена. Для полного прогона нужно обновить workflow в `server`, перенести только файл workflow в `main`, разрешить `server` в окружении `training` и выполнить **Run workflow → Branch: server**. Удалённый прогон новой конфигурации в рамках этой работы не выполнялся.

Сценарий CD проверен локально на отдельном контейнере и портах 51890/51891: первая установка и повторное обновление, отказ на неверной SHA256 до изменения установленной версии, провал HTTP-проверки у намеренно неисправного образа и автоматический откат. Проверены восстановление того же контейнера на прежнем порту и сохранение прежнего `current.json`. После проверки тестовый стенд удалён; локальный Compose-сервис на 5080 продолжает работать. Это локальная проверка сценария, а не прогон через GitHub runner.

Локально проверены новая сборка образа с SHA-тегом и меткой коммита, успешный health-ответ, отказ проверки при HTTP 404 и удаление временных контейнеров. Выполнен шаг сохранения образа из workflow: проверены SHA256 архива, загрузка через `docker image load`, совпадение ID образа и повторный успешный health-ответ. Конфигурация GitHub Actions, включая ручной запуск, прошла проверку `actionlint 1.7.7`. Проверки приложения выполнены на Windows с Docker Desktop; для облачного прогона изменения должны быть отправлены в GitHub.

Проверки Docker: `docker compose config --quiet`, `docker compose build` и `docker compose up --no-build -d` выполнены успешно. Запущенный контейнер вернул HTTP 200 и `{"status":"ok"}` по адресу `http://127.0.0.1:5080/api/v1/health`. Пользователь внутри контейнера имеет UID 1654 (не root). Контейнер оставлен работающим для локальной проверки; остановка — `docker compose down`.

В этой среде сборка и тест потребовали запуска вне ограничений песочницы; для теста использовались дополнительные параметры --disable-build-servers -m:1.
